## Требования

VPS на Linux, рекомендуемый минимум 2 vCPU / 2 ГБ RAM / 10 ГБ диска, Docker Engine с Compose v2, домен, DNS A-запись на IP сервера и открытые TCP 80/443. Выберите хостинг с доступом из России; инфраструктурный выбор и оплату делает капитан. Не используйте платформу с засыпанием или временным диском без постоянного тома.

## HTTPS через Docker Compose

```sh
git clone --branch feat/orbita-student-portal https://github.com/alexchist/mgimo-vibe-coding.git
cd mgimo-vibe-coding
cp .env.example .env
```

Замените `DOMAIN` в `.env` на свой настоящий домен. Значение должно быть только hostname, без протокола/пути. Затем:

```sh
docker compose config
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 app caddy
```

Caddy получает сертификат автоматически после правильной настройки DNS. Приложение не публикует внутренний порт наружу, принимает трафик только через reverse proxy; включены Secure-cookie, проверка origin и постоянный том SQLite. Нужен исходящий доступ Caddy к центру выдачи сертификатов. Сертификаты также сохраняются в томе.

### GigaChat в контейнере

Compose передаёт `GIGACHAT_CREDENTIALS`, `GIGACHAT_SCOPE` и необязательный `GIGACHAT_MODEL` в окружение процесса только при запуске. Храните `.env` локально с правами `0600`. Для проверки конфигурации с настроенным ключом используйте `docker compose config --quiet`, чтобы не печатать секрет. Для сборки приложения ключ не нужен.

Если требуется дополнительный CA, сохраните доверенный PEM вне checkout. Укажите его абсолютный путь в `GIGACHAT_CA_HOST_FILE` и обеспечьте только чтение файла для пользователя контейнера (UID 1000). Используйте оба Compose-файла во всех командах для этого варианта:

```sh
docker compose -f compose.yaml -f compose.gigachat-ca.yaml config --quiet
docker compose -f compose.yaml -f compose.gigachat-ca.yaml up -d --build
```

Compose монтирует PEM с хоста только на чтение, а приложение добавляет его к доверенным CA только для исходящих запросов к GigaChat. Для проверки в демоаккаунте включите отправку вопросов в Навигаторе и спросите «Что ты умеешь?» и «Как заказать справку?». При доступной модели рядом с ответом отображается её фактическое имя, а ссылки ведут в кабинет и к найденным документам. Вопрос «В какую аудиторию перенесли пару?» показывает расписание текущего студента локально.

## Проверки после размещения

1. Открыть домен по HTTPS из российской сети **без VPN**, отдельно с телефона. Зафиксировать дату, сеть и результат; проверка из облачной среды этого не заменяет.
2. Войти обоими аккаунтами из README, сравнить профили и заявки.
3. Подать тестовую заявку, перезагрузить страницу, пройти демоэтапы и скачать документ.
4. Проверить, что чужой URL заявки недоступен второму аккаунту; убедиться в Secure/HttpOnly-cookie через инструменты браузера.
5. Выполнить `docker compose restart app` и убедиться, что заявка сохранена.
6. Настроить ежедневный мониторинг и оплатить сервер минимум до 28 ноября включительно. Сделать повторную проверку перед отправкой работы.

## Сохранность и обновление

Данные находятся в именованном томе `orbita_data`. `docker compose down` сохраняет тома; **не используйте `down -v`**, если нужны заявки. Для последовательного обновления:

```sh
git pull --ff-only origin feat/orbita-student-portal
docker compose up -d --build
```

Для согласованной резервной копии остановите app, сохраните весь том (включая WAL/SHM при их наличии), затем запустите app. Не копируйте один SQLite-файл во время записи. Резервные копии не публикуются в Git. Прототип содержит только вымышленные данные, но сессии всё равно нужно считать закрытой служебной информацией.

## Ограничения

- Один экземпляр приложения с локальной SQLite. Не увеличивать число реплик без переработки хранения и сессий.
- Общедоступные демоаккаунты; нет регистрации, реального SSO, отправки в вуз и административного кабинета.
- Реальная инфраструктурная нагрузка, доступ из России и срок работы требуют внешней проверки. Они не доказаны локальными тестами.
- Образы Docker загружаются из публичного реестра. В среде без доступа к реестру сборку нужно выполнить на выбранном сервере; не отключайте TLS/проверку пакетов.

## Проверка контейнера в облачной среде разработки

14 ноября 2026 выполнены `docker compose config` с тестовым hostname и реальная сборка контейнера. В этой управляемой среде обычный `npm ci` внутри Docker сначала завершился `SELF_SIGNED_CERT_IN_CHAIN`: контейнеру не хватало доверенного CA сетевого прокси. Проверка TLS не отключалась. По инструкции cloud-environment-runtime использована временная копия Dockerfile; в оба шага `npm ci` добавлено:

```dockerfile
RUN --mount=type=secret,id=proxy_ca,required=true \
    NODE_EXTRA_CA_CERTS=/run/secrets/proxy_ca npm ci --strict-ssl=true ...
```

Она собиралась с исходным контекстом проекта и параметрами `-f /tmp/orbita-session.Dockerfile --secret id=proxy_ca,src="$CODEX_PROXY_CERT"`. Здесь многоточие обозначает сохранённые исходные аргументы `npm ci`, а `CODEX_PROXY_CERT` — предоставленный платформой путь. Сертификат использовался только как BuildKit secret: его нет в репозитории и слоях образа. Эта адаптация нужна для сетевой среды разработки; на обычном VPS используются основной Dockerfile и системное доверие к сертификатам.

Проверенный контейнер работал от `node` (UID 1000), отдавал собранные HTML и JavaScript, позволял войти, получить оценки и создать заявку. После перезапуска контейнера с именованным томом сохранялись заявка и сессия. Тестовые контейнер и том удалены. Отдельно проверена конфигурация приложения для HTTPS-прокси: разрешён ожидаемый Origin, установлен флаг Secure у cookie, чужой Origin отклонён. Это локальные проверки; настоящий сертификат домена, публичное размещение и доступ из России ещё не проверялись.
