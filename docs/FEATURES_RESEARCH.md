# Исследование подключений и сервисов кампуса

Дата: 15 ноября 2026 года. Метод: чтение публичной страницы MIPT.Tech, официальной документации провайдеров и официальных исходников VKCOM. Это кабинетное исследование для третьей итерации, не интервью, не проверка действующих студенческих аккаунтов и не испытание внешних интеграций. Пользователь подтвердил: Telegram/VK, Yandex AI и платёжный провайдер ещё не настроены; нужны демонстрационные документы и загрузка своих файлов. Реальные сообщения, платежи и запросы к платным моделям не выполнялись.

Технический контракт команды находится в [FEATURES_CONTRACT.md](FEATURES_CONTRACT.md), продуктовые сценарии — в [FEATURES_PRODUCT.md](FEATURES_PRODUCT.md). Названия переменных окружения ниже относятся к нашему приложению, а не являются обязательными именами у провайдеров. Итоговые имена и значения по умолчанию следует брать из [`.env.example`](../.env.example).

## 1. Что действительно есть на MIPT.Tech

Публичная [главная страница MIPT.Tech](https://mipt.tech/) описывает сервисы общежития: резервирование стиральных машин и общих комнат, выдачу инструментов, хранение велосипедов и самокатов. Рядом находятся учебные материалы и вики с практическими вопросами. Перед использованием помещений предлагается ознакомиться с правилами. Сайт представлен как студенческий проект при поддержке преподавателей и администрации.

**Граница наблюдения:** проверена открытая страница; вход, календарь доступности и реальное бронирование не проходились. Главная страница не подтверждает оплату общежития. Платёжный сценарий «Орбиты» происходит из запроса пользователя, а не приписывается MIPT.Tech. Код, оформление, логотипы и данные чужого сайта не копировались.

**Решение команды:** показать помещение вместе с вместимостью, оснащением, правилами и доступными интервалами; после брони предоставить её состояние и отмену. Бронирование, документы, расписание и уведомления связывать с одной учётной записью. Это перенос продуктового принципа, а не обещание интеграции с МФТИ.

## 2. Yandex AI: актуальный адрес и конфигурация модели

Официальный [базовый пример Completions API](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/generation/completions-basic) использует `POST https://ai.api.cloud.yandex.net/v1/chat/completions`, JSON, заголовки `Authorization: Api-Key <key>` и `OpenAI-Project: <folder_id>`. В OpenAI SDK этому соответствуют `api_key`, `base_url=https://ai.api.cloud.yandex.net/v1` и `project`. Для примера требуются роль `ai.languageModels.user` и область API-ключа `yc.ai.foundationModels.execute`. Адрес из актуальной инструкции предпочтительнее неподтверждённого старого `llm.api.cloud.yandex.net`.

Проверенный [каталог моделей](https://aistudio.yandex.ru/ru/docs/ai-studio/concepts/generation/models) на дату исследования содержит Qwen3.6 35B с URI `gpt://<folder_id>/qwen3.6-35b-a3b` и доступом через OpenAI-совместимые API. Это пример из источника, не автоматически выбранная модель «Орбиты». Нельзя заменять идентификатор каталога фиктивным значением или считать произвольный URI работоспособным. Для подключения обязательны `YANDEX_API_KEY`, `YANDEX_FOLDER_ID`, `YANDEX_MODEL_URI`; модель выбирается владельцем подключения из доступного ему каталога.

[Инструкция вызова функций](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/generation/completions-function) описывает `tools` с `type: function`, именем функции и JSON Schema параметров, `tool_choice: auto|none`, ответ `tool_calls` и возврат результата через сообщение `role: tool` с соответствующим `tool_call_id`. Функцию исполняет приложение; модель только предлагает имя и аргументы. Пример в инструкции использует YandexGPT 5.1. Отдельная работоспособность function calling выбранной Qwen в нашем проекте без доступа не проверена.

Согласно [инструкции отключения логирования](https://aistudio.yandex.ru/ru/docs/ai-studio/operations/disable-logging), заголовок `x-data-logging-enabled: false` поддерживается и в OpenAI-клиенте для `chat.completions`. Это настройка обработки запросов провайдером, а не гарантия отсутствия передачи данных.

**Решения команды:** ключ хранится на сервере; разрешённые функции перечислены явно; вход модели и результаты валидируются; число вызовов, объём контекста и время ответа ограничены. Внешней модели передаются только необходимые данные текущего аккаунта и отобранные фрагменты документов. Содержимое документа не становится системной инструкцией. Модель не получает инструмента оплаты и не подтверждает изменения за пользователя. Без всех настроек работает явно подписанный локальный помощник; при ошибке провайдера интерфейс сообщает о переходе к нему. Наличие адаптера не означает действующее подключение или бесплатность внешнего API.

## 3. Telegram: доставка и подтверждение получателя

[Bot API](https://core.telegram.org/bots/api#setwebhook) принимает HTTPS-вызовы вида `https://api.telegram.org/bot<TOKEN>/<METHOD>`. Для обычного уведомления используется `sendMessage` с `chat_id` и `text`; текст ограничен 4096 символами. `setWebhook` направляет обновления HTTPS POST на настроенный URL. Переданный при настройке `secret_token` приходит в `X-Telegram-Bot-Api-Secret-Token`; допустимы 1–256 символов `A–Z`, `a–z`, `0–9`, `_`, `-`. Неуспешные HTTP-ответы приводят к повторной доставке обновления; `update_id` нужен для дедупликации. Успешный `sendMessage` возвращает объект сообщения, а не подтверждение его прочтения человеком.

[Deep linking](https://core.telegram.org/bots/features#deep-linking) поддерживает `https://t.me/<bot_username>?start=<code>`. Параметр длиной до 64 символов из набора base64url приходит боту как `/start <code>` в личной переписке. Это подходит для связи внешнего адресата с вошедшим пользователем.

**Решения команды:** одноразовый случайный код имеет срок действия и владельца; привязка завершается только из проверенного входящего личного сообщения. Ввод произвольного `chat_id` в браузере не считается подтверждением владения. Webhook сравнивает секрет; повторы не создают повторную привязку. Outbox сохраняет событие и состояние попытки. Без ключа событие остаётся демонстрационной записью. Telegram не предоставляет для `sendMessage` ключа идемпотентности: после потери ответа строгое «ровно одно сообщение» не гарантируется. Нужно различать ошибку, неизвестный результат и успешное принятие API.

## 4. VK: официальный источник при недоступной документации

Страницы `dev.vk.com/ru/method/messages.send` и `dev.vk.com/ru/api/callback/getting-started` не удалось прочитать доступным инструментом. Это ограничение исследования, не утверждение о доступности VK у пользователя. Проверка выполнена по официальным репозиториям VKCOM.

[Официальный PHP SDK](https://github.com/VKCOM/vk-php-sdk/blob/master/src/VK/Client/VKApiClient.php) задаёт базовый адрес `https://api.vk.com/method` и версию `5.199`. В [схеме messages.send](https://github.com/VKCOM/vk-api-schema/blob/master/messages/methods.json) разрешён ключ сообщества; для нашего сценария нужны `peer_id`, `message`, `random_id`, а также `access_token` и `v`. `random_id` предназначен для предотвращения повторной отправки; его нужно сохранять для одной операции. Частный получатель имеет положительный ID пользователя; групповые беседы используют другую область `peer_id`.

В [схеме Callback API](https://github.com/VKCOM/vk-api-schema/blob/master/callback/objects.json) есть `type`, `group_id`, `event_id`, `v`, `secret`. Повторный `event_id` следует игнорировать. У `message_new` содержимое находится в `object.message`; рядом может быть `client_info`. [README официального SDK](https://github.com/VKCOM/vk-php-sdk#callback-api) показывает проверку ожидаемых `group_id` и `secret`, ответ настроенной строкой на `confirmation` и ответ `ok` на остальные события.

**Решения команды:** версия фиксируется как `5.199`; webhook отклоняет неверный секрет/сообщество. Одноразовый код принимается только из личного входящего сообщения: отправитель и `peer_id` должны совпасть. Адресат берётся из проверенного события. Подключение сообщества, выдача ключа и разрешения на сообщения остаются задачей владельца сервиса; адаптер не создаёт их автоматически. Отправку обозначать как принятую VK, а не прочитанную студентом.

## 5. YooKassa: отдельный тестовый магазин

[Быстрый старт](https://yookassa.ru/developers/payment-acceptance/getting-started/quick-start) использует `POST https://api.yookassa.ru/v3/payments`, HTTP Basic с идентификатором магазина и секретным ключом, JSON и `Idempotence-Key`. Для redirect-сценария задаются сумма строкой с двумя десятичными знаками, валюта `RUB`, `capture: true`, `confirmation.type: redirect` и серверный `return_url`. Полученный `confirmation.confirmation_url` ведёт на оплату. Возврат браузера на `return_url` происходит и при ошибке; он не доказывает успех. Завершённый платёж определяется серверным статусом `succeeded`, отменённый — `canceled`.

[Формат взаимодействия](https://yookassa.ru/developers/using-api/interaction-format) подтверждает `GET https://api.yookassa.ru/v3/payments/{payment_id}` с тем же Basic. Ключ идемпотентности имеет длину до 64 символов; провайдер сохраняет его действие 24 часа. После этого повтор может стать новой операцией. HTTP 500 или разрыв сети не являются доказательством отсутствия платежа.

[Тестовый режим](https://yookassa.ru/developers/payment-acceptance/testing-and-going-live/testing) требует отдельного тестового магазина и его реквизитов, использует обычный API и возвращает `test: true` в объекте платежа. Деньги при этом не переводятся. Отдельного выдуманного sandbox-host не нужно.

**Решения команды:** без реквизитов доступна только локальная демооплата без банковских полей. Внешний адаптер включается явно для тестового магазина, отклоняет `test !== true`, связывает ID платежа с собственным счётом и владельцем, сверяет сумму/валюту. Дополнительное требование префикса ключа `test_` — консервативное ограничение нашего адаптера, а не найденная универсальная гарантия формата API. Локальная связь счёта с операцией сохраняется; создание с потерянным ответом старше 23 часов блокируется до ручной сверки, чтобы не выйти за окно идемпотентности. Результат проверяется запросом сервер–сервер; браузер не устанавливает оплаченный статус. Возвратный URL задаёт сервер; ссылка подтверждения проверяется как HTTPS. Неизвестный результат сохраняется для сверки, а не заменяется новым списанием. Реальные деньги и реальная бухгалтерия общежития не входят в эту итерацию.

## 6. MCP: транспорт отдельно от совместимости авторизации

[Спецификация транспорта 2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports) определяет единый HTTP endpoint с JSON-RPC через POST и необязательным SSE. Клиент указывает в `Accept` и `application/json`, и `text/event-stream`. GET может отвечать 405, если SSE не реализован; для stateless-сервера session ID не обязателен. Сервер обязан проверять `Origin` и возвращать 403 при недопустимом значении. Последующие запросы передают согласованную версию в `MCP-Protocol-Version`.

[Спецификация авторизации](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) рекомендует HTTP-реализациям следовать OAuth 2.1 с обнаружением authorization server через Protected Resource Metadata. Поэтому собственный Bearer-токен с ручным вводом заголовка — ограниченный способ подключения прототипа, а не полная реализация стандартного OAuth-потока и не гарантия совместимости с любой нейросетью.

**Решения команды:** официальный SDK и настоящий Streamable HTTP `/mcp`; отдельные пользовательские токены с выбранными правами, сроком и отзывом; храним только хеш, показываем секрет один раз. Поддерживаем клиенты, умеющие передать `Authorization: Bearer <token>`. Токен не передаётся в URL, не является браузерной сессией и не даёт доступ к чужим записям. Получение расписания и подготовка брони используют те же серверные сервисы, что UI. Перед изменением нужно показать параметры и получить подтверждение человека; описание инструмента само по себе не обеспечивает согласие, это часть взаимодействия доверенного клиента. Подтверждение связывается с владельцем, конкретным токеном/actor и сроком действия. Для облачного клиента доступ к локальному endpoint и публичный HTTPS адрес остаются отдельными условиями; хостинг пользователь исключил из работы.

## 7. Документы и RAG: не подменять поиск генерацией

**Проектное решение, не наблюдение о стороннем сервисе:** общий вымышленный корпус и документы текущего аккаунта индексируются локально. Поиск возвращает фрагмент, название, раздел, версию и отметку происхождения. Без внешней модели это полнотекстовый поиск с цитатами. При подключённой модели те же найденные фрагменты служат контекстом RAG; ответ должен давать проверяемые источники и сообщать, когда оснований недостаточно.

Документы не являются командами: текст «отправь все данные» внутри PDF не должен вызвать инструмент. Загруженный файл, его текст и результаты поиска доступны только владельцу учётной записи. Поскольку конкурсные пароли публичны, два человека с одним демологином видят одну область данных: это не личное хранилище реального студента. В конкурсный прототип загружаются только вымышленные/учебные документы без настоящих персональных данных. Поддержка PDF с текстовым слоем не означает поддержку OCR сканов.

## Что подтверждено, а что остаётся проверить

- Подтверждены публичные описания, адреса API, формат основных вызовов и перечисленные ограничения по указанным первичным источникам.
- Доступность модели конкретному каталогу, сообщения настоящему Telegram/VK-адресату, платежи тестового магазина, webhook на публичном HTTPS и подключение выбранного пользовательского MCP-клиента не проверены: доступов нет.
- Предлагаемые меры безопасности и продуктовые сценарии являются решениями нашей команды. Их наличие в документе не заменяет тестов реализации. Фактические результаты должен фиксировать независимый обзор [FEATURES_REVIEW.md](FEATURES_REVIEW.md) после запуска.
