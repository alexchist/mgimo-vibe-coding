# Итерация 2 — техническая критика

Роль: независимый агент `critic_technical`. Прочитаны инструкции проекта, текущие `server/app.mjs`, `database.mjs`, `seed.mjs`, компоненты и существующие API-тесты. Этот документ отделяет согласование решения от последующей проверки реализации.

## Обсуждение предложений

Креативный координатор предложил четыре направления:

1. Личный план из учебных дедлайнов и собственных задач.
2. Ближайшее действие на главной, связанное с реальным пунктом плана.
3. Командный поиск Ctrl+K по текущим данным.
4. Заметки подготовки к занятиям.

Техническая оценка: объединить 1 и 2 в один законченный сценарий; 3 и 4 отложить. Поиск и заметки добавляют отдельные состояния, разрешения и интерфейсы, но не исправляют основной разрыв: карточка дедлайна сейчас ведёт к общим оценкам вместо конкретной задачи.

Исследователи передали проверенную ими опору из Canvas: личный `PlannerOverride.marked_complete` отделён от факта отправки и проверки работы. Для «Орбиты» перенимаем границу ответственности, а не код Canvas (AGPL). Основной источник: https://canvas.instructure.com/doc/api/planner.html. Точная история чтения публичных источников — в отдельных отчётах исследователей.

## Замечания к версии 1 и необходимые уточнения

| Риск | Требуемое решение |
| --- | --- |
| Добавить задачи только в seed и потерять функцию в уже опубликованной базе | `seedDatabase` возвращается сразу при существующих пользователях. Учебные пункты нужно производить из уже имеющихся дедлайнов с отдельными личными отметками либо использовать добавочную идемпотентную миграцию. Старые заявки, уведомления и сессии сохраняются. |
| Личная галочка выглядит как отправка эссе преподавателю | Отметка означает личную готовность. Нельзя менять исходный учебный дедлайн, оценку или заявлять факт сдачи. Действие обратимо. |
| Реальный текущий день делает всю демонстрационную неделю просроченной | Учебные сроки сравниваются с `referenceDate`, а контекст 16–22 ноября указан явно. Собственные даты должны использовать тот же понятный контекст либо явно отдельный режим. |
| Клиент выбирает другого владельца или подставляет произвольную ссылку | Пользователь определяется только серверной сессией. Все чтения/изменения включают `user_id` и тип записи. Источник и маршрут определяются сервером; произвольные `userId`, `sourceId`, URL не доверяются. |
| Повтор запроса переворачивает состояние обратно | PATCH принимает явный `completed: true/false`, не команду toggle. Повтор одного состояния безопасен. |
| Удаление скрывает обязательный учебный срок | Удалять можно только собственные задачи. Для учебного пункта — отказ 409; чужой или неизвестный ID — 404. |
| Некорректные или бесконечные данные | Проверять типы, нормализованную длину заголовка, настоящий календарный день и согласованный диапазон. Ограничить число собственных задач; запретить HTML-интерпретацию текста. |
| Главная и список расходятся | Оба получают одну серверную модель плана. Главная показывает первый незавершённый пункт и открывает именно его. После отметки/отмены обновляются оба представления. |

## Минимальные проверки реализации

- Два аккаунта видят разные личные задачи и отметки; прямое изменение/удаление чужого ID запрещено.
- Все изменения требуют сессии, CSRF и корректного Origin согласно существующим middleware.
- Невалидные типы, длины и календарные даты отклоняются сервером.
- Повтор PATCH с тем же boolean не создаёт дополнительного перехода.
- Отметка и отмена переживают перезагрузку и перезапуск приложения.
- Исходные учебные поля остаются прежними после личной отметки; удаление учебного пункта запрещено.
- Повторная загрузка приложения не перезаписывает существующие данные и не дублирует учебные пункты.
- Пользователь видит ошибку сохранения, не получает ложное подтверждение; на 360 px действие доступно с клавиатуры и касанием.

## Статус согласования

Версия 1: **доработать** по условиям выше. Координатор прислал версию 2, сохранив учебные данные отдельно от личного состояния, выбрав явный контекст демо-недели и дополнительное хранение без сброса базы.

Версия 2: **принято техническим критиком**. Согласованный контракт:

- `bootstrap.plan = {items, referenceDate}` и `GET /api/plan` строятся одной серверной функцией.
- Пункт `{id, kind: 'deadline' | 'personal', title, subject, dueDate, completed, sourceRoute?}`.
- Учебный ID совпадает с существующим ID дедлайна; поля получены из текущего источника, личная отметка хранится отдельно с владельцем. Собственные задачи получают серверный UUID.
- `POST /api/plan`: `title` после trim 1–120 символов, `dueDate` отсутствует/null либо настоящий календарный день 16–22 ноября 2026 года; максимум 100 собственных задач.
- `PATCH /api/plan/:id`: только `completed: boolean`; попытка изменить учебные поля не должна создавать видимость их редактирования.
- `DELETE /api/plan/:id`: только собственная личная задача; учебная — 409, чужая/неизвестная — 404.
- `#plan/:id` открывает конкретный пункт из главной; отсутствие срока, весь план выполнен и ошибка сохранения — отдельные понятные состояния.

На момент согласования реализация и тесты нового плана ещё не проверены. Последующие фактические результаты добавляются отдельно.

## Проверка реализованного решения

После сигнала тимлида о завершении интеграции выполнен независимый `node --test tests/planner.test.mjs`: **9/9 результатов** (8 сценарных подпроверок и 1 родительская группа), без failures/skips. База создаётся в отдельном временном каталоге, а не в пользовательском `data/`.

Проверки подтвердили:

- План появляется и в базе существующей установки; ранее прочитанное уведомление и сохранённая заявка не сбрасываются.
- Bootstrap и отдельный GET возвращают одну модель; повтор чтения не дублирует учебные пункты.
- Все маршруты защищены сессией, все записи — CSRF и Origin. Чужие личные и учебные ID нельзя изменить или удалить.
- Подмена владельца/источника/маршрута, неправильные поля, типы, длины и даты отклоняются сервером.
- Личная готовность не меняет исходную учебную запись. Повтор одного PATCH безопасен; отмена готовности сохраняется после перезапуска.
- Собственная задача и её удаление сохраняются после перезапуска. Лимит 100 личных задач действует; удаление освобождает место.

Статическое чтение `server/planner.mjs` подтвердило фильтр пользователя и типа записи во всех операциях, guard владельца при upsert отметки и отсутствие записи в учебный источник. Проверка произвольного URL не требуется для данных задачи: маршруты источника разрешены серверным списком, а пользовательская форма URL не принимает.

Также просмотрены `getPlanFocus` и новый компонент: ошибочное URI-кодирование хеша обрабатывается через try/catch; неизвестный или чужой ID не интерполирует чужие данные и показывает только собственный список. Интерфейс использует результат успешной серверной записи, отделяет ошибку обновления списка от ошибки сохранения и не объявляет локальную галочку отправкой работы. Полный мобильный/браузерный прогон выполняется отдельным тестировщиком.

Блокирующих технических замечаний к проверенным API-сценариям нет. Это ограниченная проверка прототипа, а не аудит эксплуатационной безопасности многопользовательской университетской системы.
